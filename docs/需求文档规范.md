# AI 编程时代的需求文档规范

> 用途：把需求交给 AI 开发前，用这份结构把边界写死。
> 核心原则：**你留白的地方，等于交给了 AI 的默认值。**

---

## 零、两条元规则

### 规则一：禁止形容词，只允许数字和枚举

| 不要写 | 要写 |
| --- | --- |
| 支持高并发 | 峰值 50 QPS，同时在线 200 人 |
| 数据量不大 | 单表 10 万行以内，日增 300 条 |
| 响应要快 | 首屏 1.5s 内，接口 P99 < 200ms |
| 尽量保证不丢 | 允许丢最近 5 分钟数据，更早的必须持久化 |
| 兼容老数据 | 兼容 2025-06 之后的记录，更早的忽略 |

形容词对人有用，对执行无用。AI 无法把"高并发"翻译成一个具体的锁策略。

### 规则二：验收标准由人写，AI 只负责实现

AI 自己定义标准、自己写测试、自己实现，等于自证清白。测试全绿说明不了任何事。
**每个需求条目后面必须跟一条人能独立判断的验收条件。**

---

## 一、目标与不做的事

### 1.1 一句话目标
用一句话说清这件事解决什么问题。不要写愿景。

### 1.2 明确的禁止项（必填）
这一节比"要做什么"更重要。AI 会顺手做你没要求的事，必须提前封住。

- 不允许引入新依赖：`（列出允许的依赖白名单，其余一律不加）`
- 不允许改动的文件/模块：`（列出路径）`
- 不允许自行扩展的功能：`（例如：不要加缓存、不要加重试、不要加异步队列）`
- 不允许改动的接口契约/数据结构：`（列出字段名或 schema）`
- 不允许自行修改配置项、环境变量、部署脚本

### 1.3 明确不做
把「这次不做但看起来相关」的东西列出来，否则 AI 会"顺便做了"。

---

## 二、数据与规模

### 2.1 数据结构
字段名、类型、是否可空、取值范围、默认值。有就贴 schema，没有就列表格。

### 2.2 数量级（必填数字）
- 单条记录大小：`__ KB`
- 总量：`__ 条 / __ MB`
- 增长速度：`每天 __ 条`
- 保留期限：`__ 天，之后归档/删除`

### 2.3 读写比例
读 `__%` / 写 `__%`。这决定要不要加索引、要不要缓存（要，就写明"要"，别留白）。

### 2.4 数据来源与可信度
- 来源：`（API / 抓取 / 用户输入 / 内部生成）`
- 是否可能重复、乱序、缺失：`（是/否，及处理方式）`
- 字段是否可能为空：`（列出允许为空的字段）`

---

## 三、并发与一致性

> 这一节是 AI 最不会主动处理的。它默认假设"一次只有一个请求"。
> 每一项都必须填，不适用就写「不适用」并说明理由。

### 3.1 并发画像
- 峰值 QPS：`__`
- 峰值时段：`（例如每天 9:00-10:00）`
- 同时在线用户：`__`
- 是否会突发（例如活动、定时任务同时触发）：`（是/否）`

### 3.2 竞态点清单
逐个列出"可能被两个请求同时修改的资源"：

| 资源 | 并发场景 | 期望行为 |
| --- | --- | --- |
| 例如：某条记录的 count 字段 | 两个用户同时点赞 | 最终值 = 实际点赞数，不能丢更新 |
| 例如：定时任务的执行 | 多实例同时触发 | 只能有一个执行，其余退出 |

### 3.3 幂等
- 哪些接口必须幂等：`（列出）`
- 幂等键怎么定：`（用户ID+业务ID / 请求ID / 内容哈希）`
- 重复请求的期望返回：`（返回首次结果 / 返回错误码 __）`

### 3.4 锁与事务
- 需要锁的地方：`（列出）`，粒度：`（行/表/分布式）`
- 锁的实现倾向：`（乐观锁 / 悲观锁 / 串行队列）`——**必须指定，不要让 AI 自己选**
- 事务边界：`（哪几个操作必须原子完成）`
- 允许的最长事务时间：`__ ms`

### 3.5 一致性等级
- 强一致 / 最终一致：`（选一个）`
- 若最终一致，收敛时间上限：`__ 秒`
- 允许的不一致窗口内的用户体验：`（例如：可能看到旧值，文案需提示"更新中"）`

### 3.6 排序与顺序
- 是否要求严格顺序处理：`（是/否）`
- 乱序到达的处理：`（丢弃 / 按时间戳重排 / 覆盖）`

---

## 四、失败与降级

### 4.1 外部依赖清单
逐个写"挂了会怎样"：

| 依赖 | 超时 | 失败策略 | 是否可降级 |
| --- | --- | --- | --- |
| 例如：数据库 | 3s | 重试 2 次，仍失败返回 503 | 不可降级 |
| 例如：第三方 API | 5s | 返回上一次缓存数据 + 标注数据时间 | 可降级 |
| 例如：对象存储 | 10s | 跳过该文件，记录失败清单 | 可降级 |

### 4.2 禁止静默失败（硬性要求）
- 所有异常必须记录日志，包含：时间、模块、入参摘要、异常类型、堆栈
- 不允许 `catch` 之后返回空数组/空对象/null 当作正常结果
- 不允许吞掉错误后继续执行后续步骤

### 4.3 重试策略
- 哪些操作允许重试：`（列出）`
- 最多重试次数 / 间隔（退避）：`__ 次 / __ ms，指数退避`
- 哪些操作**禁止**重试：`（写操作、非幂等操作）`

### 4.4 部分失败
多步骤流程中某一步失败时：`（整体回滚 / 保留已完成部分 / 标记待补偿）`

---

## 五、安全与权限

### 5.1 认证与授权
- 谁可以调用：`（匿名 / 登录用户 / 管理员）`
- 越权检查：哪些资源必须校验归属：`（列出）`

### 5.2 输入校验
- 长度上限、类型、格式白名单
- 明确要求：所有外部输入必须校验，不允许直接拼进 SQL / 命令 / 文件路径 / 模板

### 5.3 敏感数据
- 哪些字段是敏感的：`（密钥、手机号、token）`
- 要求：不进日志、不进错误上报、不出现在 URL 里
- 存储：`（明文 / 加密 / 哈希）`——必须指定

### 5.4 速率限制
- 接口级限流：`__ 次 / __ 分钟 / 每 IP`
- 超限返回：`429 + 说明`

---

## 六、可观测性

### 6.1 日志
每个关键步骤至少一条日志，字段包含：`时间 / 模块 / 操作 / 关键ID / 结果 / 耗时`

### 6.2 指标
需要暴露的数值：`（请求量、失败率、耗时分布、队列积压）`

### 6.3 排查路径
出问题时按什么顺序查：`（先看什么日志，再看什么指标）`

---

## 七、验收标准（由人写，可执行）

每条需求对应一条能独立判断的验收条件。格式：

```
[需求编号] 验收：
- 输入：___
- 期望：___
- 判定方式：___（人工检查 / 自动脚本 / curl 返回码）
```

**至少覆盖这四类：**
1. 成功路径
2. 边界（空、超长、非法格式、重复提交）
3. 并发（同时 N 个请求，结果是什么）
4. 失败（依赖不可用时是什么表现）

---

## 八、对 AI 执行过程的约束

这一节约束的不是代码，是 AI 的工作方式。

1. **先出方案，再写代码。** 实现前先给出：改哪些文件、加哪些依赖、有哪些实现选项和取舍。人确认后再动手。
2. **一次只做一件事。** 不要把多个需求混在一次提交里。
3. **不许扩大范围。** 发现别处有问题，只报告，不顺手改。
4. **改动必须可解释。** 每个关键实现给一句话说明为什么这么选。
5. **自检清单**：实现完成后逐条对照第七节验收标准，输出「已验证 / 未验证」，不允许默认通过。
6. **不确定就问。** 需求里有歧义的地方，停下来问，不要猜。

# 附：填好的示例

> 场景：一个每天定时抓取数据、落库、生成 JSON 给前端展示的小系统。
> 注意每一处都是"数字或枚举"，没有形容词。

## 1. 目标
每天 06:00 抓取 3 个来源的条目，归一化后存储，产出 `latest.json` 供静态站读取。

## 1.2 禁止项
- 不引入新依赖（只允许：`axios`、`dayjs`）
- 不改动 `src/view/**`
- 不加缓存层、不加消息队列
- 不改 `latest.json` 的字段名
- 不改部署脚本

## 1.3 不做
不做实时更新，不做用户订阅，不做历史图表。

## 2. 数据
- 单条：约 400 字节
- 总量：约 5000 条 / 2MB
- 增长：每天 200 条，保留 180 天，之后删除
- 读写比：写 1 次/天，读 N 次/天（静态文件，不涉及数据库读写压力）
- 来源可能重复：同一条目按 `id + source` 去重

## 3. 并发
- 峰值 QPS：写 0（定时任务），读走静态文件
- 并发点：**定时任务在多个 runner 同时触发** → 期望：只有一个执行，其余立即退出（用文件锁或分支锁）
- 幂等：抓取任务必须幂等，同一天重复跑产出完全相同的 JSON（除 `fetchedAt` 字段）
- 事务：无数据库，不涉及
- 一致性：最终一致，允许 `latest.json` 延迟最多 1 个抓取周期
- 顺序：不要求严格顺序，条目按 `publishedAt` 倒序输出

## 4. 失败
| 依赖 | 超时 | 失败策略 | 降级 |
| --- | --- | --- | --- |
| 来源 A API | 5s | 重试 2 次（间隔 1s、2s） | 失败则用上一次成功数据，页面标注数据时间 |
| 来源 B 网页 | 10s | 重试 1 次 | 同上 |
| 写入产物 | — | 失败则整体不提交 | 不可降级 |

- 禁止静默失败：抓取失败必须打印来源名 + 错误类型，并且**不允许用空数组覆盖上一份数据**
- 部分失败：允许部分来源成功，此时合并新旧数据，并在 `meta.partial = true`

## 5. 安全
- 无认证（只读静态文件）
- 抓取目标 URL 白名单固定 3 个，不允许从外部输入拼 URL
- API key 只从环境变量读，不写入产物、不进日志
- 限流：对每个来源不超过 1 次/分钟

## 6. 可观测
- 每次运行打印：来源名、抓取条数、耗时、是否降级
- `latest.json` 带 `meta: { fetchedAt, partial, sourceStatus: {} }`

## 7. 验收
1. 正常：产出 JSON 条目数 > 0，字段齐全，`meta.fetchedAt` 为当日
2. 边界：来源返回空时，**保留上一份数据**，`meta.partial = true`，不能覆盖成空
3. 并发：手动同时触发两次，第二次检测到锁后退出，产物只被写一次
4. 失败：断网重跑，进程以非 0 退出，且旧数据未被破坏

## 8. AI 执行约束
- 先给实现方案，确认后再写
- 不改 `src/view/**`
- 完成后逐条对照第 7 节，输出验证结果

---

# 怎么用

1. 复制上面的模板，填完七节。填不出来的地方就是你还不知道的地方，先问清楚再交给 AI。
2. 把「禁止项」和「验收标准」当成合同条款，不是建议。
3. AI 交付后，先看它有没有越界（有没有加你没要求的依赖、有没有改范围外文件），再看验收结果。
4. 每次出问题，回头看是哪一节没写。缺的那一节，下次补进模板。
