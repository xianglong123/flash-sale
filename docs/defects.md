# 缺陷记录（Defects Log）

维护规则：

- 一条缺陷一个编号，编号不复用，不重排。
- 状态只有 `OPEN` / `FIXED` / `CLOSED` 三种。
- 每条必须包含：现象、复现步骤、根因、修复方式、回归证据。没有回归证据的修复不算修好。

## P0-001 · 缓存层不可达时返回 500 而不是 503

| 项 | 内容 |
|---|---|
| 级别 | P0 |
| 状态 | **FIXED**（2026-11-23） |
| 发现方式 | 压测阶段故障演练 |
| 影响面 | 全部依赖 Redis 的接口（下单、活动详情、统计） |

### 现象

Redis 进程停止后：

```
POST /api/seckill/13/order
{"code":"INTERNAL_ERROR","message":"系统错误"}
HTTP 500   耗时 0.51s

GET /api/seckill/13/stats   → HTTP 500
```

500 的语义是「服务端 bug」，会触发告警、误导调用方；而实际是依赖降级，应该是 503「稍后重试」。需求文档第 6 节（失败与降级）明确要求依赖不可用时降级，实现不符合契约。

### 复现

```bash
brew services stop redis
sleep 3
curl -i -X POST http://127.0.0.1:8080/api/seckill/<id>/order -H "X-User-Id: 1"
```

### 根因

Lettuce 连接失败被 Spring Data Redis 翻译成 `org.springframework.dao.QueryTimeoutException: Redis command timed out`（因为 `spring.data.redis.timeout=500ms`），它一路冒到全局兜底的 `Exception` handler，被统一翻译成 500。

**这里我第一版修复是错的**：凭经验去捕获 `RedisConnectionFailureException` 和 `RedisSystemException`，改完重测，仍然是 500。看日志栈才发现实际类型是 `QueryTimeoutException`。教训：异常类型不能猜，必须从栈里读。

### 修复

`GlobalExceptionHandler` 改为捕获父类 `org.springframework.dao.DataAccessException`，统一降级为 503：

```java
@ExceptionHandler(org.springframework.dao.DataAccessException.class)
public ResponseEntity<Result<Object>> onDependencyDown(Exception e) {
    // 503 SYSTEM_NOT_READY：缓存层不可用，请稍后重试
}
```

选父类而不是具体类的原因：Redis 的连接失败可能被翻译成 `QueryTimeoutException`、`RedisConnectionFailureException`、`RedisSystemException` 等多种类型，逐个列举必然有漏。数据库访问异常同属该父类，归为 503 在语义上也正确（依赖不可用），而 `DuplicateKeyException` 已由更具体的 handler 优先处理，不受影响。

### 回归证据

| 用例 | 修复前 | 修复后 |
|---|---|---|
| Redis 停机后下单 | 500 `INTERNAL_ERROR` | **503 `SYSTEM_NOT_READY`**（0.64s） |
| Redis 停机后查统计 | 500 | **503** |
| Redis 停机后访问管理接口（无 token） | 401 | **401**（鉴权优先，未被降级逻辑吞掉） |
| 契约要求 | 降级而非报错 | ✅ |

### 遗留风险

DB 的 `DataAccessException` 也会被归为 503。语义上没错（依赖不可用），但运维侧需要能从日志区分「缓存挂了」和「数据库挂了」，目前靠 `[DEGRADE]` 日志里的异常类名判断。

## P0-002 · Redis 重启后没有自动预热，活动永久不可下单

| 项 | 内容 |
|---|---|
| 级别 | P0 |
| 状态 | **FIXED**（2026-11-23） |
| 发现方式 | 压测阶段故障演练 |
| 影响面 | 全部进行中/未开始的活动 |

### 现象

Redis 数据清空后，所有活动一律返回 `503 SYSTEM_NOT_READY`，且**不会自愈**。只要运维不手动重新「启动」活动，业务就一直是死的。等价于「缓存重启 = 大促停摆」。

### 根因

库存、活动时间窗、幂等集合只存在于 Redis，写入点只有两个：创建活动（`create`）和启动活动（`start`）。系统没有任何从数据库重建缓存的路径。

数据库里的 `seckill.available_stock` 也不能直接用 —— 它只是创建时的快照，下单只改 Redis 不改它，读出来是错的。

### 修复

新增三个组件，从订单表（唯一事实源）重建缓存：

| 组件 | 职责 | 触发时机 |
|---|---|---|
| `WarmUpService#rehydrate` | 重建单个活动的库存 / 元数据 / 幂等集合 | 被调用 |
| `WarmUpRunner` | 启动时重建全部未结束活动 | `ApplicationReady`（`@Order(2)`） |
| `WarmUpJob` | 运行期只补丢失的活动 | 每 60 秒（`fixedDelay`） |

三个关键设计约束：

1. **库存用 `SETNX` 写，绝不覆盖**。如果 Redis 还有实时值，用 DB 快照去覆盖会直接把已扣掉的库存「还回去」，制造超卖。
2. **库存 = 总库存 − 已成交订单数 − 未解决异常单数**。异常单是「已预扣库存但未落库」的记录，必须扣掉，否则重建瞬间就多出库存。
3. **幂等集合从订单表回填**。缓存丢失时 `seckill:user:{id}` 也一起没了，不回填的话同一用户可以重复下单，等于绕过全部幂等防线。

启动预热失败不阻断启动（Redis 可能还没就绪），交由 60 秒定时任务兜底。

### 回归证据

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 缓存清空 + 应用不重启，立即下单 | 503（永久） | 503（预期，缓存确实为空） |
| 同上，等待 60 秒后再下单 | 503（永久） | **200 成功**，库存由定时任务重建 |
| 缓存清空 + 应用重启 | 503（永久） | **启动即重建，12 个活动全部恢复** |
| 重建库存准确性 | — | 活动 13：总库存 1000、成交 25 → 重建 stock = **975** ✅ |
| 幂等集合回填 | — | 回填 25 人；已成交用户 771 再次下单 → **409** ✅ |
| 三方对账（DB 26 单 / Redis 974） | — | 一致 ✅ |

### 遗留风险

- 单活动订单量很大时（实测 3 万单），回填幂等集合约需 90 ms（按 1000 条一批 SADD），可接受；如果将来单活动到百万级，需要改成异步或惰性回填。
- 「展示用最近成交列表」不重建，缓存丢失后该列表为空，属可接受降级。

## P1-001 · IP 维度限流会误杀 NAT 用户，造成大规模少卖

| 项 | 内容 |
|---|---|
| 级别 | P1（策略问题，非崩溃） |
| 状态 | **OPEN** |
| 发现方式 | 压测阶段专项实验 |

**现象**：库存 1000、100 个真实用户共用同一出口 IP（公司 / 学校 / 4G 基站），实际只成功 20 单，80 个请求被 429 拒绝，**少卖 980 件**。

**根因**：`IP 维度 20 次/秒` 把一整个 NAT 出口的所有用户当成一个人。

**建议**：阈值可配置；已认证用户只按 `user_id` 限流，IP 限流只用于未认证流量；或把 IP 阈值提高到与业务规模匹配的量级。

**未修原因**：涉及产品策略，需要业务方定阈值，不是纯代码问题。

## TOOL-001 · 压测脚本伪 IP 生成碰撞，结论差点失真

| 项 | 内容 |
|---|---|
| 级别 | 工具类（不影响生产） |
| 状态 | **FIXED**（2026-11-23） |

**现象**：轮次 4 中 k6 报告 30000 请求「全部合法状态码、0 失败」，但数据库只有 7503 条订单。

**根因**：`uid = __VU * 1000000 + __ITER + 1`，而 1000000 恰好是 250 和 62500 的整数倍，模运算后 IP 高两位恒定，2000 个 VU 只映射到 200 个 IP，全部撞在 IP 限流上。

**修复**：改用 32 位哈希打散 IP。

**这件事的价值**：如果当时只看 k6 的 `0 failed`，会得出「30000 并发零失败」的假结论并写进报告。是「成功数 = DB 行数」这一步对账救了它。
