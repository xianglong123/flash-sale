# 秒杀 P0 压测报告

- 日期：2026-11-23
- 被测版本：`flash-sale` commit `dddc922`（P0）
- 环境：本地 macOS 单机
- 压测工具：k6 v2.4.0

一句话结论：**在 1000~30000 库存、200~2000 并发的 5 个有效轮次里，成交数全部精确等于库存数，零超卖、零少卖、零异常单。吞吐上限由 MySQL 决定（约 1880 个成功订单/秒），不是 Redis。同时也测出三个必须修的问题 —— 其中两个 P0 已于当天修复并回归（见第 6、7 节）。**

---

## 0. 这次压测要回答三个问题

1. **会不会超卖**：并发把库存扣成负数？
2. **能扛多少**：单机吞吐上限在哪，瓶颈是谁？
3. **哪里先倒**：压力上来后第一个失效的组件是什么？

为了让结论站得住，每一轮都必须做三方对账，而不是只看 HTTP 返回码：

| 判据 | 期望 |
|---|---|
| 成功数（HTTP 200） | 精确等于库存，不能多 1 个，也不能少 1 个 |
| `seckill_order` 表行数 | 等于成功数 |
| Redis `seckill:stock:{id}` 剩余 | 等于 库存 − 成功数，且 ≥ 0 |
| `reconcile` 异常单 | 等于 0 |

只看返回码是自欺欺人：代码完全可能返回 200 而根本没写库。这次轮次 4 就差点踩进去。

## 3. 结论一：零超卖，5 个有效轮次全部精确

| 轮次 | 库存 | 成功数 | DB 订单数 | Redis 剩余 | reconcile |
|---|---|---|---|---|---|
| 1 | 1000 | 1000 | 1000 | 0 | 0 |
| 2 | 2000 | 2000 | 2000 | 0 | 0 |
| 3 | 2000 | 2000 | 2000 | 0 | 0 |
| 5 | 30000 | 30000 | 30000 | 0 | 0 |
| 6 | 30000 | 30000 | 30000 | 0 | 0 |

**误差全部为 0**。既没有超卖 1 件，也没有少卖 1 件，Redis 扣减与 DB 落库没有出现漂移，补偿表一条记录都没产生。

这四条防线各自起了作用：

1. **Lua 原子预扣**：`GET stock → 判断 → DECR → SADD user` 在同一段脚本里执行，Redis 单线程保证原子性，不存在读改写的竞态窗口。
2. **Redis Set 幂等**：同一用户第二次进来直接被 `SISMEMBER` 挡住。
3. **DB 唯一索引兜底**：`UNIQUE(user_id, seckill_id)` 在应用层判断失效时兜住重复写入，并翻译成 409 而不是 500。
4. **落库失败不回滚 Redis**：宁可记异常单后续补齐，也不回滚 —— 回滚会重新引入竞态，反而制造超卖。

## 4. 结论二：瓶颈是 MySQL，不是 Redis

把"被拒绝的请求"和"成功下单的请求"分开看，性能画像完全不同：

| 路径 | 吞吐 | P95 延迟 | 说明 |
|---|---|---|---|
| 售罄拒绝（轮次 3） | 4249 req/s | 342 ms | 只做 Redis 判断，不写库 |
| 全部成功（轮次 5/6） | 1881 req/s | 1250 ms | 每笔都要 MySQL insert |

延迟构成（应用内埋点 `seckill.deduct.latency`，累计 108551 次采样）：

- Lua 扣减平均 **11.77 ms**、最大 143 ms
- 整体请求平均 1.02 s（2000 并发、全部成功时）

也就是说：扣减只占总延迟的约 1%，其余 99% 花在**等数据库连接 + insert + 返回**上。Hikari 30 个连接就是吞吐天花板：2000 并发争 30 个连接，队列自然把 P95 推到 1.2 秒。

这一点值得记住：**秒杀系统的性能从来不是"Redis 够不够快"，而是"数据库能不能吞下所有成功的订单"**。Redis 扣减快，只是把压力准时、整齐地转交给数据库而已。

另外，Lua 扣减 11.77 ms 这个数字偏高（本地 Redis 单次 RTT 应在亚毫秒级）。原因是 Spring Data Redis 默认 Lettuce 单连接共享，2000 并发全部排队在同一条连接上。这也解释了为什么限流拒绝的路径 P95 仍有 30~50 ms。

## 5. 结论三：IP 限流会误杀真实用户（产品级问题）

这是本次压测最有价值的发现，也是我一开始完全没意识到的。

**实验**：库存 1000（充足），100 个不同用户，全部来自同一个出口 IP（模拟公司 / 学校 / 4G 基站的 NAT 场景）。

结果：

```
20 个 200（成功）
80 个 429（限流拒绝）
DB 订单 20，Redis 剩余 980
```

库存明明够 100 个人买，实际只卖出去 20 件，**少卖 98%**。

原因：`IP 维度 20 次/秒` 的限流在 NAT 场景下等于把一整个办公楼的用户当成一个人。真实秒杀里，这类流量占相当比例。

这不是代码 bug，是策略问题。可选方向：

1. 把 IP 限流阈值提上去（比如 200/s），交给用户维度 + 全局维度兜底；
2. IP 限流只在"未登录 / 无 X-User-Id"的请求上生效，已认证用户只按 user_id 限流；
3. 阈值做成配置项，按大促规模动态调整 —— 至少不能写死在代码里。

作为对照，单用户 1 秒内连点 10 次的表现是正确的：

```
200 429 429 429 429 429 429 429 429 429
订单数 1
```

## 6. 故障演练：Redis 丢了 / 挂了

**先更正上一版报告的一个错误结论。** 我最初写的是「Redis 数据丢失后返回 503，符合预期」—— 那次 Redis 被 brew 的 launchd 自动拉起并加载了 RDB 快照，数据根本没丢，我只是看到 503 就下了结论。真正复现要 `flushall` 之后 `save` 把空库落盘。这和轮次 4 的 IP 碰撞属于同一类错误：**没真正验证，就以为验证过了**。

修复前实测：

| 场景 | 表现 | 判定 |
|---|---|---|
| Redis 完全不可达 | `500 INTERNAL_ERROR`，0.51 s | ❌ 应为 503 |
| Redis 数据清空（应用不重启） | `503 SYSTEM_NOT_READY`，且永久 | ❌ 无法自愈 |
| 脏订单 | 0 | ✅ 不超卖 |

修复后重测（2026-11-23）：

| 场景 | 修复后 |
|---|---|
| Redis 不可达 → 下单 | **503 `SYSTEM_NOT_READY`**（0.64 s） |
| Redis 不可达 → 查统计 | **503** |
| Redis 不可达 → 管理接口（无 token） | **401**（鉴权优先，没被降级逻辑吞掉） |
| 缓存清空、应用不重启，立即下单 | 503（缓存确实为空，正确） |
| 同上，等 60 秒 | **200 成功**（定时任务已重建） |
| 缓存清空、应用重启 | **启动即重建 12 个活动** |
| 重建库存准确性 | 活动 13：总库存 1000、成交 25 → stock = **975** |
| 幂等集合回填 | 25 人；已成交用户 771 再下单 → **409** |

自愈重建的三条硬约束（写进代码注释了）：库存必须 `SETNX` 写入，不能覆盖实时扣减值；库存 = 总库存 − 已成交订单 − 未解决异常单；幂等集合必须从订单表回填，否则重建后同一用户可重复下单。

## 8. 复现方法

```bash
# 1. 起依赖（本机 MySQL 需手动拉起，见 README）
redis-cli ping
MYSQL_PWD=12345678 mysql -h127.0.0.1 -uroot -e "SELECT 1;"

# 2. 起应用
cd flash-sale
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
mvn spring-boot:run

# 3. 建活动并启动
T=dev-only-token-please-change-0123456789abcdef
curl -X POST http://127.0.0.1:8080/api/admin/seckill \
  -H "Content-Type: application/json" -H "X-Admin-Token: $T" \
  -d '{"itemName":"压测","price":99,"totalStock":1000,"durationSeconds":1800}'
curl -X POST http://127.0.0.1:8080/api/admin/seckill/<id>/start -H "X-Admin-Token: $T"

# 4. 压测
BASE=http://127.0.0.1:8080 SECKILL_ID=<id> VUS=200 ITER=10000 k6 run loadtest/k6-seckill.js

# 5. 三方对账
MYSQL_PWD=12345678 mysql -h127.0.0.1 -uroot -N \
  -e "SELECT COUNT(*) FROM flash_sale.seckill_order WHERE seckill_id=<id>;"
redis-cli get seckill:stock:<id>
```

## 9. 这次压测我自己犯的错误（必须记录）

轮次 4 一开始给出的是"服务端有问题"的信号：30000 请求全部返回合法状态码、k6 统计 0 失败，但 DB 只有 7503 条订单。第一反应是"大并发下丢单了"，很吓人。

查下来是**我的压测脚本错了**。伪 IP 生成用了：

```js
const a = (uid % 250) + 1;
const b = (Math.floor(uid / 250) % 250) + 1;
const c = (Math.floor(uid / 62500) % 200) + 1;
```

而 `uid = __VU * 1000000 + __ITER + 1`。`1000000` 恰好是 `250` 和 `62500` 的整数倍，做模运算后高两位恒定，只剩 VU 编号在 `c` 上以 16 为步长循环。结果 2000 个 VU 只映射到 200 个 IP，每个 IP 挤了 150 个请求，全部撞在 `20 次/秒` 的 IP 限流上。

修正为 32 位哈希打散后（轮次 5、6），30000 请求全部成功，DB 30000 条，一条不差。

**这件事的意义超过压测本身**：如果我当时没做"成功数 = DB 行数"这一步对账，只看 k6 的"0 failed"，我会得出"30000 并发全成功、系统完美"的结论，然后把它写进文档发出去。数据自洽的假结论，比明确的失败更危险。

这也是我坚持每条结论都要三方对账的原因 —— 工具会骗你，你自己的脚本也会骗你。
