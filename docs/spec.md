# flash-sale · 规格与验收契约（spec）

> **这份文档和 `requirement.md` 的分工**
>
> - `spec.md`（本文）——**当前生效的契约**。只写外部可观察的行为、约束和判定方法，不写实现手段。给 AI 执行、给人验收，两边读同一份。
> - `requirement.md`——业务规则、架构禁令、决策理由的历史记录。写于实现之前，保留追溯价值。
>
> 两者冲突时以本文为准。本文的每条验收判据都标了**当前实际状态**，这是它和需求文档最大的不同：需求写"应该"，契约写"验过没有"。

**目标一句话**：库存 1000 件，瞬时并发下精确卖出 1000 单，不超卖、不少卖、不重复下单。

**冲突裁决顺序**：`不超卖 > 不少卖 > 响应速度 > 功能完整`。宁可少卖，不可超卖。

---

## 1. 用户场景

**S1 观众**：打开展示页，看到商品、价格、进度条、剩余与已售数量、最近成交、倒计时。只读，不需登录。

**S2 参与者**：点"立即抢购"，系统在毫秒级给出确定结果——成功拿到订单号，或明确告诉他为什么没拿到（售罄 / 已参与 / 太频繁 / 未开始 / 已结束 / 系统暂不可用）。

**S3 运营者**：在管理页创建活动、设定库存与时长、开始、结束、观察实时数据。需要令牌。

## 2. 功能需求（FR）

> 句式统一为"当…时，系统应…"，每条都能被外部观察验证，不含实现偏好。

### 2.1 浏览

- **FR-01** 当观众访问展示页且存在进行中的活动时，系统应展示商品名、单价、总库存、已售数、剩余数、状态与倒计时。
- **FR-02** 当展示页轮询时，系统应以 1500ms 间隔返回最新数据，且最近成交列表最多 10 条、用户标识仅保留后 4 位。
- **FR-03** 当展示数据滞后时，页面应明示"实时库存以提交结果为准"，不得让展示值被理解为承诺。

### 2.2 下单判定

判定必须按下列顺序，前五步全部在缓存层完成，不查库：

- **FR-04** 当活动不存在时，系统应返回 `404`，且不产生任何库存变动。
- **FR-05** 当请求不在活动时间窗内时，系统应返回区分"未开始"与"已结束"的明确状态，不得统一返回售罄。
- **FR-06** 当请求频率超过限制时，系统应返回 `429`，且不消耗库存。
- **FR-07** 当同一用户对同一活动重复请求时，系统应固定返回 `409 ALREADY_PARTICIPATED`（不接受"有时返回原订单号、有时返回错误码"的随机语义）。
- **FR-08** 当库存不足时，系统应返回 `409 SOLD_OUT`，且不产生订单记录。
- **FR-09** 当以上检查全部通过时，系统应原子扣减 1 件库存并写入 1 条订单，两者不可只成功其一。

### 2.3 管理端

- **FR-10** 当管理端请求缺少或携带错误令牌时，系统应返回 `401`，且不透露令牌格式的任何信息。
- **FR-11** 当运营者创建活动时，库存取值应限于 `1 ~ 100000`，越界返回 `400`。
- **FR-12** 当活动处于未开始状态时，系统应允许增减库存；活动进行中时只允许增加。
- **FR-13** 当运营者尝试减少库存时，系统应一律拒绝（`400 STOCK_DECREASE_FORBIDDEN`），任何状态下都不允许。

## 3. 容量与延迟（NFR）

| 项 | 目标 | 说明 |
| --- | --- | --- |
| 峰值 QPS | 2000（下单接口） | 单机本地压测口径 |
| 并发用户 | 10000，5 秒内到达 | 验收目标 |
| 单场库存 | 1000（演示）/ 30000（容量测试） | |
| 成功数 | 恰好等于库存数 | 其余必须"明确拒绝"，不许超时或 500 |
| 接口延迟 | P99 < 200ms（2000 QPS 下） | 见第 8 节实际达成情况 |
| 一致性收敛 | 缓存与库 5 秒内对齐 | 展示允许 1 秒滞后 |

## 4. 失败语义（不可协商）

| 场景 | HTTP | 错误码 | 可重试 | 备注 |
| --- | --- | --- | --- | --- |
| 活动不存在 | 404 | NOT_FOUND | 否 | |
| 未开始 | 409 | NOT_STARTED | 是（到点后） | |
| 已结束 | 409 | ENDED | 否 | |
| 已售罄 | 409 | SOLD_OUT | 否 | |
| 已参与 | 409 | ALREADY_PARTICIPATED | 否 | |
| 触发限流 | 429 | RATE_LIMITED | 是，退避后 | |
| 缓存不可用 | 503 | SYSTEM_NOT_READY | 是 | 降级，不是故障 |
| 全局开关关闭 | 503 | SYSTEM_BUSY | 是 | 人工止血 |
| 未知异常 | 500 | INTERNAL_ERROR | 否 | 必须带 traceId |

**禁止项**：`catch` 后返回 `200` 空响应；吞掉缓存异常继续走库；把失败伪装成成功或伪装成售罄。

## 5. 依赖降级

| 依赖 | 超时 | 失败时行为 |
| --- | --- | --- |
| 缓存 | 500ms | 直接拒绝（503），**禁止绕过缓存直连数据库扣减** |
| 数据库 | 3s | 下单失败，**不回收已扣库存**，落异常单交人工核对 |
| 活动元数据 | — | 返回"未就绪"（503），不得返回"售罄" |

**关键取舍**：缓存扣减成功但落库失败时，不回滚缓存。理由：回滚会与新扣减交叉产生竞态，而少卖 1 件可接受、超卖不可接受。"看起来更完整的自动回滚"在这里是有害的。

**自愈要求**：缓存中的活动元数据丢失后，系统应能自行重建，且不得覆盖已扣减的实时库存。重建库存须满足：

```
重建库存 = 总库存 − 已成交订单数 − 未解决异常单数
```

漏掉"未解决异常单"就是制造超卖。

## 6. 明确不做（Out of scope）

| 不做 | 理由 |
| --- | --- |
| 支付、履约、物流、退款 | 秒杀是"资格获取"，全链路不在本次验证范围。支付用 mock |
| 用户注册登录、会话体系 | 下单侧靠请求头传 id，这是演示前提，不构成真实身份 |
| 购物车、优惠券、多商品拼单 | 价格是固定单价，加了就要引入价格计算与分摊，与并发验证无关 |
| 消息队列削峰 | 引入 MQ 会把"同步落库"的瓶颈变成"队列积压"，问题被隐藏而不是被解决 |
| 分布式锁、限流框架、本地缓存框架 | 能力用缓存原生命令和框架自带组件即可，加框架等于用封装掩盖并发风险 |
| 库存分段、预扣池、多级缓存 | 单键原子扣减在 30000 库存下已验证可行，分段是多余复杂度 |
| 风控模型、图形验证码、人机识别 | 只做频率限制。设备指纹与行为识别是独立课题 |
| 多机房、分布式事务、跨区容灾 | 单机验证，这些属于部署形态问题 |
| 运营后台的权限分级、审计合规 | 只有一个静态令牌，够用于演示；真实后台需要 RBAC，不在本次范围 |
| Docker、容器编排、云上部署 | 验收在本地 macOS 完成，容器化属于交付形态问题 |
| 移动端适配、WebSocket 推送 | 桌面浏览器 + 轮询足够，实时推送的复杂度与收益不成正比 |

## 7. 边界情况与假设

**假设**（不成立则需重新评估规格）

1. `X-User-Id` 由调用方提供，系统信任它——这只在演示场景下成立。
2. 单场库存上限 10 万，超过则内存与单键扣减的假设需要重新论证。
3. 压测与服务同机（12 逻辑核），因此性能结论偏保守；换成独立压测机数字会上浮。
4. 缓存是单实例、单连接共享，多分片场景下原子性需重新设计。
5. 时钟以单机为准，活动时间窗不跨时区。

**边界**

- 库存扣到 0 的瞬间并发请求：全部返回售罄，绝不出现负库存，也不出现多卖。
- 活动结束与最后一单同时发生：以扣减成功为准，订单有效；结束后不再接受新单。
- 缓存刚重建的瞬间（库与缓存尚未对齐）：以重建值为准，允许短暂保守（宁可少卖）。
- 同一用户 1 秒内连点 10 次：恰好 1 单成功，其余为限流或已参与，不允许出现 2 单。

## 9. 已知缺陷与未决问题

**已知缺陷（不在本次修复范围，需业务拍板）**

- **NAT 限流误杀**：单 IP 20 次/秒按"一个人"处理整个出口，100 人共用一个 IP 时只成 20 单，少卖 98%。这是**策略问题不是代码缺陷**：阈值该定多少、已认证流量是否该按用户维度限流，需要业务决定。

**未达标**

- 全成功路径吞吐与 P99 均未达到 NFR 目标。瓶颈不在扣减（内部埋点显示扣减仅占约 1% 延迟），在写库队列与连接池上限。要达标应改这里，不是把扣减写得更花哨。

**完成度说明**

本契约共 22 条判据，当前验证状态：**12 条已验证、2 条有数据未达标、2 条未实现、4 条未实测、2 条路径从未触发**。

未实测的条目不算完成——这正是 `requirement.md` 里"应支持"和本文"验过了"的差别。下次拿这份表逐条打勾，比任何"已完成"的口头结论都可靠。

**待决**

- 管理令牌默认值仍写在配置文件里，应改为环境变量注入。
- `AC-15` 的异常单路径从未真实触发，属于"代码存在但未验证"——按本契约标准，它不算完成。
